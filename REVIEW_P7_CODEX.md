# Phase 7 adversarial code review

Reviewed commit `bcc2da9` as a full-state review of the phase-7 files, against `DESIGN_HOLDER_BRAIN_SPLIT.md`. Findings are ordered by severity.

1. **BLOCKER — reverse migration can consume an exit status after its last C2 check, then emit that session as live.** The brain's early drain loop only observes the current pending-event count (`daemon/src/holder_mode.rs:1474`), and the holder performs its sole authoritative scan immediately before arming (`holder/src/holder.rs:1174`). After it sends the OK (`holder/src/holder.rs:1223`), a live child can exit before the brain exits. On the next poll, the holder deliberately processes pidfds before the channel (`holder/src/holder.rs:805`, `holder/src/holder.rs:822`), so if the pidfd and brain EOF are both ready it calls `waitid`/consumes the status first (`holder/src/holder.rs:815`, `holder/src/holder.rs:873`). The supervisor then takes the already-armed rollback and execs the monolith (`holder/src/main.rs:338`, `holder/src/main.rs:352`) without another C2 check; `rollback_manifest` merely reuses the pre-exit record (`holder/src/holder.rs:526`). The resulting manifest describes a live child whose only wait status has already been consumed. At best the monolith gets `ECHILD`/`ESRCH` and loses that status; role validation can instead reject the whole handoff and lose every session. Once `split_rollback` is armed, the holder must stop consuming exits and leave them as zombies for the monolith, or atomically revalidate on EOF and abort/respawn a brain if it has consumed any status.

2. **BLOCKER — holder self-reexec has no channel quiescence or deploy-operation serialization.** `HolderClient` explicitly permits pipelined requests and protects only individual writes (`daemon/src/holder_mode.rs:354`, `daemon/src/holder_mode.rs:371`); independent RPCs run on independent connection threads (`daemon/src/lib.rs:1190`). `daemon.upgrade_holder` is restart-barrier-exempt (`daemon/src/control/dispatch.rs:333`, `daemon/src/control/dispatch.rs:347`) and ignores daemon state entirely (`daemon/src/control/dispatch.rs:1836`). Meanwhile the holder's `FrameReader` is a local variable (`holder/src/holder.rs:647`), and the upgrade snapshot contains neither its partially received bytes/SCM_RIGHTS FDs nor `armed_deploy` (`holder/src/holder.rs:418`). The holder accepts `reexec_holder` even when another deploy is armed (`holder/src/holder.rs:1230`) and execs as soon as its outbound replies drain (`holder/src/holder.rs:862`). Two concrete failures follow: (a) a request split between the old reader's userspace buffer and the socket is irrecoverably desynchronized in the new holder; (b) concurrent `daemon.restart` and `daemon.upgrade_holder` frames can arm a new brain pin and then snapshot without that arm, so the brain exits after an accepted restart but the upgraded holder respawns the old current pin. SCM_RIGHTS received with a partial request can also disappear at exec. Add an exclusive brain-side holder-operation gate, drain all pending holder calls to a verified frame boundary, refuse upgrade while `armed_deploy` is set, and prevent new sends until rehello completes.

3. **BLOCKER — the S15 gate does not test the previous brain pin.** The design requires the candidate holder to negotiate with the *actual current previous pin* (`DESIGN_HOLDER_BRAIN_SPLIT.md:212`). The implementation only checks whether the candidate holder's advertised range covers the currently running brain's compiled range (`daemon/src/holder_mode.rs:1543`, `daemon/src/holder_mode.rs:1550`). For example, previous brain `1..=1`, old holder `1..=2`, current brain `2..=2`, and candidate holder `2..=2` passes this code; a subsequent current-brain failure leaves both attempts at the previous pin in `proto_mismatch`/`HELD_DOWN`. The matrix still substitutes the baseline brain for the previous pin (`scripts/holder-skew-matrix:10`, `scripts/holder-skew-matrix:67`) even though phase 6 now has real pins. Preflight the candidate-holder/previous-pin pair itself (or obtain an equivalent negotiation proof from those exact pinned inodes), and run that exact lineage cell.

4. **BLOCKER — migration preserves a stale holder-upgrade bootstrap variable, which takes precedence over the valid migration manifest.** `do_execveat_with_argv` removes only `CM_REEXEC_*` variables before injecting the v4 manifest pointer (`daemon/src/reexec.rs:1532`, `daemon/src/reexec.rs:1547`). Holder boot checks `CM_HOLDER_UPGRADE_MANIFEST_FD` first and checks the migration variable only in an `else if` (`holder/src/main.rs:155`, `holder/src/main.rs:179`). Thus a stale numeric `CM_HOLDER_UPGRADE_MANIFEST_FD` in the monolith's service environment makes the new holder attempt that unrelated FD, enter its fresh-boot failure branch, and never inspect the valid v4 manifest. The live sessions and listener are then outside holder state. Every cross-image exec must scrub both bootstrap namespaces (preferably one shared allowlist policy) before adding exactly the intended pointer.

5. **BLOCKER — an empty durable TUI flip file fails open to monolith mode.** The code treats a readable but empty `~/.cm/holder-binary` exactly like an absent file (`tui/src/daemon_launch.rs:229`, `tui/src/daemon_launch.rs:246`), despite the adjacent promise to fail closed on an unreadable marker (`tui/src/daemon_launch.rs:248`). A crash between truncate and write, a partial deployment, or an accidental blank file therefore makes the next TUI launch silently start the monolith on a migrated host—the precise C6 failure the marker is meant to prevent. Only `NotFound` should mean “no flip”; any present file that is empty, malformed, non-absolute, or unusable must refuse launch. The runbook should also prescribe temp-file + fsync + atomic rename and verification.

6. **BLOCKER (cm-manager rollout) — the systemd runbook orders the binary copy after the launch-mode flip and leaves the token restart ambiguous.** The prerequisites first tell the operator to restart once for the token and to change `ExecStart` (`DESIGN_HOLDER_BRAIN_SPLIT.md:371`), but only afterward say to scp both binaries (`DESIGN_HOLDER_BRAIN_SPLIT.md:375`). A crash after the flip but before the copy makes `Restart=always` invoke a missing holder. If the operator edits both prerequisites and performs the single requested restart afterward, systemd starts a fresh holder before live migration, terminating the monolith path instead of performing the same-PID handoff. The safe sequence must be explicit: atomically stage and verify both binaries; add token while `ExecStart` still names the monolith and restart/verify the monolith; then change `ExecStart` and `daemon-reload` without restarting; finally call migration. Reverse migration needs the same explicit inverse ordering.

7. **SHOULD-FIX — corrupt-manifest “fresh boot” leaves the cleared escrow open and can preserve an unsupervised old brain.** Both invalid-manifest branches continue in the same process with `Holder::new` (`holder/src/main.rs:168`, `holder/src/main.rs:193`). The preceding exec intentionally made the escrow inheritable (`daemon/src/migrate.rs:244`; `holder/src/main.rs:805`), but these failure branches neither own/close it nor restore CLOEXEC. On a failed holder-upgrade manifest, exec does not trigger PDEATHSIG because the holder PID did not die, and the still-open channel prevents EOF, so the old brain can continue serving while the “fresh” holder attempts to spawn another brain with no knowledge of the sessions/listener. On migration failure, the unowned listener can keep the socket bound and prevent the fresh brain from starting. Since this failure class already concedes session loss, fail-stop is safer: exit so the kernel closes all authority and the supervisor performs a genuinely fresh start, or close a process-wide known-safe FD range without consulting untrusted manifest numbers before fresh boot.

8. **SHOULD-FIX — every successful phase-7 exec leaks its executable target as a non-CLOEXEC, unowned FD.** Migration clears `holder_fd` with the manifest escrow (`daemon/src/migrate.rs:244`, `daemon/src/migrate.rs:246`), but migration boot owns only manifest-named FDs (`holder/src/main.rs:503`) and never adopts the holder target. Holder upgrade similarly clears the candidate `pin` (`holder/src/main.rs:805`, `holder/src/main.rs:807`), while upgrade boot adopts only manifest fields (`holder/src/main.rs:735`). Reverse migration clears the monolith target (`holder/src/main.rs:880`, `holder/src/main.rs:882`), but the standard handoff owns the distinct `rollback_dup`, not that target (`daemon/src/reexec.rs:1936`). These FDs survive success, leak into later brains/session children, and accumulate across holder upgrades. Keep ELF exec targets CLOEXEC if supported by the exec shape, explicitly close/re-CLOEXEC the target at earliest new-image startup, or include it as a named, single-owner manifest field.

9. **SHOULD-FIX — the holder-upgrade manifest has structural validation but no FD-role/identity validation; migration also probes roles before confirming it is a migration schema.** `read_holder_manifest` verifies file identity, seals, checksum, schema, bounds, and duplicate numbers (`holder-proto/src/holder_manifest.rs:267`, `holder-proto/src/holder_manifest.rs:349`) but never verifies that channel/listener/master/pidfd/pin FDs have their claimed kernel roles or that pidfds match the recorded PIDs/starttimes. `upgrade_boot` immediately converts those numbers to `OwnedFd` and holder authority (`holder/src/main.rs:730`, `holder/src/main.rs:737`; `holder/src/holder.rs:472`). Sealing prevents post-write mutation, not a writer/version-skew bug that assigns the wrong role. Conversely, migration calls `validate_fd_roles` before its v4-only schema check (`holder/src/main.rs:487`, `holder/src/main.rs:493`), so a valid standard v3 manifest is rejected as a holder migration only *after* escrow FDs were probed, violating the no-escrow-touch-before-complete-validation rule. Add holder-manifest role and PID identity probes before ownership, and reject non-v4 migration shape before any named-FD probe.

10. **SHOULD-FIX — C8 still has a fallible operation between a successful arm and process exit.** The source claims “nothing fallible” at `daemon/src/holder_mode.rs:1409`, but after the arm reply succeeds it calls `eprintln!` (`daemon/src/holder_mode.rs:1432`, `daemon/src/holder_mode.rs:1438`) before `process::exit`. Rust stderr printing can panic on a write error. If stderr is broken, the deploy thread unwinds while the brain stays alive and the holder remains armed for up to 30 seconds; an unrelated brain death in that window fires the stale deploy/rollback. Move all formatting/logging before arm, then use an allocation-free/best-effort write whose error is ignored followed immediately by `_exit`/`exit`.

11. **SHOULD-FIX — rollback-record identity is not bound to its envelope, and age fields can be materially stale by exec time.** `rollback_record` keys storage by body `uid`/incarnation but deliberately stores the JSON unparsed (`holder/src/holder.rs:1101`, `holder/src/holder.rs:1142`). Projection patches only the four FD/PID fields (`holder/src/holder.rs:538`, `holder/src/holder.rs:545`) and trusts the blob's own `uid`; the standard manifest validator does not enforce unique session UIDs (`holder-proto/src/reexec_manifest.rs:1046`, `holder-proto/src/reexec_manifest.rs:1081`). A skew/logic bug can therefore store A's envelope with blob uid B and later attach A's PTY/pidfd to B, possibly duplicating B. Patch or validate `uid` as holder-owned identity. Separately, all age-valued cells are captured once before the sequential per-session request stream (`daemon/src/holder_mode.rs:1364`, `daemon/src/holder_mode.rs:1386`; `daemon/src/reexec.rs:1399`). A slow holder or large session set makes the monolith reconstruct activity/done times too recently by the entire transfer delay. Carry a capture timestamp/elapsed adjustment or compose each record as late as possible under a bounded bulk transfer. I found no analogous reason to overwrite `watcher_checkpoint` or cgroup metadata: those are brain-authored under the quiesce/safe-point contract.

12. **SHOULD-FIX — the rollout's required verification surface is missing, and holder build identity is stale after upgrade.** `daemon.health` exports no `brain_pid`, `breaker_state`, or holder `brain_restarts`, even though the rollout/redeploy recipes tell the operator to inspect those (`DESIGN_HOLDER_BRAIN_SPLIT.md:365`, `DESIGN_HOLDER_BRAIN_SPLIT.md:208`). The holder status response already contains breaker/restart/build fields (`holder-proto/src/channel.rs:388`), but health discards all except sessions/pending count and uses the build ID cached at initial connect (`daemon/src/control/methods.rs:3458`, `daemon/src/control/methods.rs:3499`). Rehello merely logs the upgraded holder's ID (`daemon/src/holder_mode.rs:284`) and cannot update the immutable cached string, so the prescribed “holder_build_id changed” check (`DESIGN_HOLDER_BRAIN_SPLIT.md:380`) reports the old value until the brain restarts. Export the current process PID and the live status fields, source holder identity from each status/rehello, and make the runbook name keys that actually exist (`build_id`, not the separately promised but absent `brain_build_id`).

13. **SHOULD-FIX — legacy preflight classification can both run a real daemon and accept a real preflight failure.** `brain_deploy_preflight` relies on a fixed supposedly nonexistent directory (`daemon/src/holder_mode.rs:1230`, `daemon/src/holder_mode.rs:1244`) but never proves it is absent/non-directory. If it exists and is writable—particularly for a root-run service—a legacy binary can bind and proceed into a full daemon boot, duplicate restore work, and make `.output()` hang. The classifier also accepts any nonzero result whose stderr contains the generic phrase `failed to bind cm-daemon socket` (`daemon/src/holder_mode.rs:1272`, `daemon/src/holder_mode.rs:1278`); a genuine modern preflight/config failure that includes that text is misclassified as a legacy success. Use a per-invocation path whose parent is a securely created regular file (guaranteed `ENOTDIR`), and require an exact sentinel containing that path and errno, or add a side-effect-free compatibility probe that cannot fall through to serving.

14. **SHOULD-FIX — the phase-7 tests cover four happy maneuvers but omit the specified failure/skew boundaries that expose the findings above.** The migration file contains exactly happy migration, forced post-validation rollback, happy reverse migration, and same-build holder upgrade (`daemon/tests/holder_split_migration_e2e.rs:330`, `daemon/tests/holder_split_migration_e2e.rs:398`, `daemon/tests/holder_split_migration_e2e.rs:455`, `daemon/tests/holder_split_migration_e2e.rs:513`). The upgrade copies the same binary and never checks a changed holder build ID (`daemon/tests/holder_split_migration_e2e.rs:538`). The skew scenario exercises negotiation, spawn, one crash/adopt, and teardown (`daemon/tests/holder_skew_e2e.rs:213`, `daemon/tests/holder_skew_e2e.rs:301`), while the design promises deliberate no-overlap→breaker→rollback, redelivery, checkpoints/listeners, and SCM_RIGHTS violations across versions (`DESIGN_HOLDER_BRAIN_SPLIT.md:324`, `DESIGN_HOLDER_BRAIN_SPLIT.md:330`). Add deterministic tests for the C2 late-exit race, concurrent arm+holder-upgrade, a fragmented/in-flight frame across upgrade, previous-pin no-overlap, invalid manifests with inherited escrow, exec-failure flag restoration, stale bootstrap env, incarnation high-water after upgrade, rollback-record identity/age behavior, and empty flip-file fail-closed semantics.

15. **SHOULD-FIX — pidfd acquisition failure after parked-brain spawn leaks an unreaped child.** `spawn_parked_brain` creates the child, then returns immediately if `pidfd_open` fails (`daemon/src/migrate.rs:356`, `daemon/src/migrate.rs:359`). The comment correctly notes that dropping `Child` neither kills nor waits (`daemon/src/migrate.rs:363`), but that is exactly what the function then does on success and what unwinding does on this failure. The channel eventually drives the child to exit, but the monolith has no retained handle/pidfd with which to reap it, leaving a zombie until daemon termination. On post-spawn setup failure, kill and `Child::wait` before returning; only drop `Child` after pidfd ownership is established.

## Checks that held

- The migration parked brain is spawned synchronously on the same per-connection thread that calls `execveat`: connection threads are created at `daemon/src/lib.rs:1190`, dispatch is inline at `daemon/src/lib.rs:1301`, and migration is called inline at `daemon/src/control/dispatch.rs:1806`. That upholds the documented PDEATHSIG creator-thread requirement.
- Incarnation stamping is present on the common `HolderPending::arm` path (`daemon/src/holder_mode.rs:1025`) used after both spawn and adopt, migration mints fresh values (`holder/src/holder.rs:376`), and holder upgrade restores `next_incarnation` (`holder/src/holder.rs:481`).
- The listed-FD failure restoration is present for holder upgrade and reverse migration (`holder/src/main.rs:838`, `holder/src/main.rs:897`). Migration pre-exec failures restore the full flag snapshot (`daemon/src/migrate.rs:297`). The trusted migration-rollback exec does not restore flags on failure, but its caller immediately terminates the holder (`holder/src/main.rs:211`), so those descriptors cannot leak into later children.

Focused checks run during review were green: `cargo test -p cm-holder-proto -p cm-holder` (64 tests total) and `cargo test -p cm-daemon --test holder_split_migration_e2e --test holder_skew_e2e` (6 tests). Their success does not cover the races and failure paths above.

## Verdict

**Not fit to deploy yet.** Findings 1–5 gate even the local phase-7 rollout: the reverse escape hatch is not status-safe, holder upgrades are not transactionally isolated or previous-pin-safe, migration can select the wrong bootstrap manifest, and the local supervisor flip is not fail-closed. Finding 12 also needs resolution (or an explicit, tested out-of-band verification procedure) before the first local fire-and-verify migration. Finding 6 separately gates the cm-manager rollout. After those gates and regression tests for findings 1–5 are fixed, the code is a reasonable candidate for a local-only soak; the remaining should-fix items should be closed before declaring phase 7 complete or proceeding fleet-wide.

# Daemon-side workflow orchestration for headless feedback workflows

## Summary

Finish moving the workflow run loop into `cm-daemon` so a feedback workflow keeps iterating (worker -> reviewer -> manager) on an always-on host with no live TUI. Most of the daemon machinery already exists (the `WorkflowPoller`, `DaemonWorkflowResolver`, transcript introspection, and the daemon-routed `workflow_transition` / `workflow_done` handlers). The remaining work is to move the three things still done by the TUI tail — target-role history append, activation-prompt delivery to the PTY (with its PTY-quiet/keyboard-mode-aware Enter scheduling), and fresh-context respawn — plus a daemon-side `start_workflow` that can spawn participants. The TUI then becomes a pure observer. Finally, enable it on `cm-manager` with headless Claude + Codex auth.

## Problem

When the laptop goes offline the TUI stops and every run freezes — even though the participant sessions run inside `cm-daemon` on `cm-manager` and stay alive. The daemon already *decides and fires* static `on_idle` transitions for daemon-owned runs (`daemon/src/workflow/poller.rs`), but the actual hand-off does not complete headlessly because:

1. The next role's history entry is appended by the TUI tail, not the daemon. Without it, the daemon poller skips the run forever as `SkipReason::NoHistoryEntry` (`poller.rs:516`, `poller.rs:161`).
2. The rendered activation prompt is delivered to the participant PTY by the TUI tail (`tui/src/workflow/controller.rs:2255` `deliver_dynamic_activation_prompt`), so with no TUI the next role is never prompted and sits idle.
3. Fresh-context respawn (`/clear`, transcript-id swap, baseline reset) is done by the TUI tail (`controller.rs:2465` `reset_fresh_session`), so the reviewer role can't reset headlessly.

There is no way to start a feedback chain and let it finish while the operator is offline (e.g. on a flight). The cloud push/pull worker (`worker/startup.sh`) is a dead end: one `claude` in tmux, no orchestration, a resumed session gets no prompt and sits idle. The autonomous one-shot worker path is out of scope here.

## Goals

- A feedback workflow started against the `cm-manager` daemon keeps iterating worker -> reviewer -> manager to completion with NO local TUI process running.
- Reattaching the TUI afterward shows the full run history (state.json `history` + events.jsonl) and live state for any still-running run.
- Existing semantics preserved exactly: static `on_idle` fires only after the outgoing role produces a NEW assistant message; fresh-context respawn swaps `session_id` in place while the sidebar slot survives; activation-prompt template indices are relative to launch time (per-role baselines).
- The daemon is the single control plane for ALL runs; the TUI never drives a run (chosen end state — daemon always drives).

## Non-goals

- The autonomous one-shot cloud worker path and its push/pull persistence fix (`worker/startup.sh`, GCS re-upload on normal completion). Tracked separately.
- New workflow features (new roles, transition kinds, template variables). This is a relocation of existing behavior.
- A web/remote observation UI. The TUI over `ssh-unix` host transport remains the observation surface.
- Reworking the already-shipped daemon transcript introspection or the `WorkflowPoller` gate/decision logic — those stay; we extend them.

## Current state

The workflow control plane is already mostly daemon-resident. What exists vs. what is still TUI-only:

### Already in the daemon (do not rebuild)

- State model + disk I/O: `daemon/src/workflow/run.rs` — `WorkflowRun`, `RoleBinding` (`current_session_id`, `daemon_session_uid`), `MessageBaseline`, `HistoryEntry`, `TriggerKind`, atomic RMW under `state.json.lock`; `active_assistant_start_count()` reads the baseline from the most recent history entry.
- Static-path driver: `daemon/src/workflow/poller.rs` — `WorkflowPoller` ticks every 250ms, `collect_snapshots` reads disk via `run::load_all()`, `evaluate_snapshot` runs the idle gate (`assistant_turn_completed_since(engine, wt, sid, baseline)`), renders the activation prompt via `DaemonWorkflowResolver` (`poller.rs:1052`), and `fire_static_transition` (`poller.rs:606`) calls the shared `workflow_transition` handler with `expected_from` + `trigger="static_idle"`.
- Ownership gate: `daemon_owns_run` (`poller.rs:880`) — daemon drives a run iff `role_sessions[active].daemon_session_uid` is set AND that uid is live in `state.sessions`. The TUI's controller skips exactly those runs (`controller.rs` `daemon_session_uid.is_some()` skip).
- Transcript introspection: `daemon/src/workflow/transcript.rs` — `assistant_turn_completed_since`, `count_messages`, `list_messages`, `latest_plan` (for both Claude and Codex). Parity with the TUI's `crate::agent` impl is pinned by a cross-crate test.
- Template engine + resolver: `daemon/src/workflow/template.rs::render` + `DaemonWorkflowResolver` (`poller.rs:1052-1166`) implementing `RoleResolver` with baseline-relative `skip(offset)` slicing.
- State-mutating RPCs: `workflow_transition`, `workflow_done`, `workflow_reject_finding`, `stop_workflow`, `get_workflow_state`, `list_workflows` (`daemon/src/control/methods.rs`). `workflow_transition` mutates state.json under flock — `close_active_role`, `iteration += 1`, `active_role = to` (`methods.rs:3478`) — and then appends the event (`methods.rs:3319`+). The event is written AFTER the mutation; it is a notify/deliver signal, not a re-apply trigger.
- PTY lifecycle + manifest broadcasts: `start_session` / `kill_session` / `mcp_start_session`, per-session `PtyByteFanout`, `manifest.watch` (`daemon/src/manifest.rs`).

### Still TUI-only (the residual to move)

- Target-role history append: the daemon `workflow_transition` mutates close/iteration/active_role but does NOT push the incoming role's `HistoryEntry`. The TUI tail does it via `append_history_entry_for_event_target_role` inside `run::modify` (`controller.rs:1637`-1662), patching `assistant_count_at_start` from `compute_role_assistant_count` (`controller.rs:2223`). Headless => no entry => `poller.rs` returns `NoHistoryEntry` forever.
- Activation-prompt delivery: `deliver_dynamic_activation_prompt` (`controller.rs:2255`) renders the prompt (or uses the poller-supplied one), runs fresh-reset if needed, and calls `agent.submit_prompt`. Delivery is a deferred `PendingWrite::wait_for_quiet` drained by the TUI main loop when the PTY goes quiet, with the Enter keystroke scheduled separately ~10s later; engine-specific Enter encoding (Codex kitty keyboard mode) is chosen by the drainer at fire time from the LIVE terminal mode (`tui/src/agent/mod.rs:83-89`, `make_prompt_pending_write` at `agent/mod.rs:154`, kitty drain in `tui/src/app.rs:6180`/`13710`).
- Fresh-context respawn: `reset_fresh_session` (`controller.rs:2465`) queues `/clear` gated on PTY-quiet, invalidates the bound sid + baseline, and lets the transcript correlator rebind the new sid.
- Launch / session spawning: `start_workflow` routes to `~/.cm/tui.sock` (`mcp_server/server.py:557`). The TUI reads the TOML, builds engine-specific argv/env/cwd, spawns participants (the daemon's `start_session` takes a fully-formed argv/env/cwd — command construction is explicitly TUI-side per `methods.rs:174`, `:206`, `:568`), delivers the worker's initial prompt, and writes the initial state.json.

The in-code comments already name these as planned slices: `controller.rs:2251-2254` ("2c-2 / 2c-3 move this delivery (and the fresh-respawn it triggers) to the daemon too; at that point this helper is deleted alongside `fire_transition`"). This doc specifies those slices.

## Proposed design

Extend the existing daemon poller/handlers; do not add a parallel engine. There is exactly ONE state mutation per hand-off — already performed under flock inside `workflow_transition` / `workflow_done` (or the poller's `fire_static_transition`, which calls the same handler). Everything this doc adds is downstream of that single mutation and must be idempotent and driven off RUN STATE, never off replaying events.

```
        ONE mutation (exists today)                       NEW: daemon completes the hand-off
  workflow_transition / poller fire           ----->  handler records a durable "pending activation"
     close_active_role; iteration++; active_role=to        on the run (NO history entry yet)
     append event (notify only)                               |
  workflow_done                                                v
     close_active_role; active_role=None;            daemon delivery drainer (keyed off run state):
     status=Done  (NO incoming role, NO history)       1. if target role is Fresh: fresh reset first
                                                          (/clear, swap sid, reset baseline)
                                                        2. compute POST-reset assistant_count_at_start
                                                        3. append/patch the incoming role's history entry
                                                        4. submit prompt to owned PTY when quiet,
                                                           schedule Enter per live keyboard mode
```

### A. Activation-finalization: fresh reset first, THEN history append (resolves reviewer High #1)

The incoming role's `HistoryEntry` must NOT be appended inside `workflow_transition` itself, because for `Context::Fresh` roles the `assistant_count_at_start` baseline must be the POST-reset count. The TUI path is explicit about this ordering: it defers the append until after `deliver_dynamic_activation_prompt` runs the fresh reset, then computes the post-reset count (`controller.rs:1463-1493`, `:1575`). The daemon gate reads the baseline from the latest history entry, not from `role_baselines` (`run.rs:292` `active_assistant_start_count`, consumed at `poller.rs:516`), so a baseline recorded before the reset cannot be corrected by a separate `MessageBaseline` reset that runs afterward — for fresh reviewer activations it would wedge or prematurely fire `on_idle`.

So `workflow_transition` records only a durable "pending activation" alongside its existing close/iteration/active_role mutation — it does NOT append history. The record must carry everything finalization needs to reconstruct the history entry AND render the prompt WITHOUT re-reading events.jsonl (so it survives a daemon restart mid-finalization): target role, the RAW supplied prompt (NOT pre-rendered — see the rendering note below), `needs_fresh_reset` flag, monotonic activation id, finalization phase, AND the full trigger/history metadata that today is threaded through the event — the post-mutation `iteration`, and the trigger payload (`from_role` for both kinds; for `McpTransition` also the originating `prompt` and `event_id`; the `static_idle` discriminator for `StaticIdle`). These are exactly the values the transition handler captures inside the closure today and copies onto the event (`event.from_role` at `methods.rs:3530`, `event.iteration` at `methods.rs:3536`, `args.trigger` from the params) — they get written onto `pending_activation` in the same closure instead of being left only on the event.

Rendering happens at finalization, not at record time. An MCP `workflow_transition` passes a RAW prompt string (`mcp_server/server.py:953`), and the TUI today renders that prompt — or, if it's empty, falls back to the target role's `subsequent_activation_prompt`/`activation_prompt` template — then expands it via the resolver before delivery (`controller.rs:2350`). The daemon must reproduce this at finalization: compute `template_source = supplied_prompt if non-empty else (subsequent_activation_prompt if the role has prior activations else activation_prompt)`, then render it with `DaemonWorkflowResolver` — rendering BEFORE the `/clear`, matching the TUI, which renders at `controller.rs:2372` before `reset_fresh_session` at `:2387`. Render-before-`/clear` preserves existing semantics: a fresh role's template that references its own transcript (e.g. its prior-iteration `this_turn`) sees the pre-`/clear` content, exactly as today. The change versus the current daemon poller (which pre-renders at poll time — also before the reset) is to render ONCE at finalization, from the persisted raw prompt + the frozen pre-reset/pre-append snapshot, rather than pre-rendering in the poller.

The daemon delivery drainer then performs an explicit activation-finalization, in order: (1) render the prompt via `DaemonWorkflowResolver` from the PRE-reset, PRE-append run snapshot (so a fresh role's template that references its own transcript sees the pre-`/clear` content — TUI renders at `controller.rs:2372` before resetting at `:2387` — and so `prior_activations` counts only entries strictly before this activation — `controller.rs:2331`, the TUI appends at `:1637` after rendering), apply the empty→template fallback above, and freeze the rendered text onto `pending_activation`; (2) if the target role is Fresh, run the fresh reset (`/clear`, reset `MessageBaseline` to 0, clear `current_session_id`, snapshot the transcript-dir listing for the post-delivery rebind); (3) set the new entry's baselines — FRESH: both 0 (the post-`/clear` transcript is empty, nothing to read or count); PERSISTENT: `assistant_count_at_start` via `transcript::count_messages` (assistant TURN count, includes tool-only / thinking-only entries; feeds the idle gate) and `text_messages_at_start` via `transcript::list_messages(…, Assistant).len()` (text-bearing count; feeds `this_turn` slicing) on the stable sid — two different counters for two consumers, exactly as the TUI keeps them (`controller.rs:2055-2067`); (4) append (or patch) the incoming role's history entry (counts from step 3; `session_id` = the stable sid for a persistent role, left pending for a fresh role; `TriggerKind` from the persisted metadata); (5) deliver the frozen prompt; (6) FRESH role ONLY — AFTER delivery, run daemon sid discovery (section C) to rebind `current_session_id` to the new transcript and patch the entry's `session_id`; the idle gate stays inert (poller `NoTranscriptId` skip) until that rebind lands. A crash after the append (step 4) resumes delivery from the frozen text rather than re-rendering against the now-larger history (which would flip `prior_activations` and pick the wrong template). The TUI's deferred append is then removed. After finalization the poller never wedges on `NoHistoryEntry`. `TriggerKind` parity (`StaticIdle{from_role}` vs `McpTransition{from_role, prompt, event_id}`) is preserved because finalization reads the persisted metadata rather than the event.

Rollback scope: the existing append-event-exhaustion rollback restores only the daemon-owned fields `workflow_transition` changed — `active_role` and `iteration` (field-targeted, `methods.rs:3574`). Recording `pending_activation` in the same closure adds a daemon-owned field, so the rollback must also remove (or restore the prior value of) `pending_activation`; otherwise an exhausted append leaves the old active role restored but an orphan pending activation pointing at the target role, which the drainer would deliver against a role that is no longer active.

Note `workflow_done` is out of this scope: it closes the active role and sets `status = Done` with NO incoming role and NO new history entry (`methods.rs:3768`, `run.rs:336-340`). It records no pending activation.

### B. Activation delivery via a durable pending-activation record (resolves reviewer High #2 + open question 1)

Because delivery is inherently asynchronous (wait for PTY-quiet, then a separately-scheduled Enter), activation is NOT done synchronously inside `workflow_transition`. The durable pending-activation from section A is consumed by a daemon-side delivery drainer (extending the `WorkflowPoller` tick, or a sibling drainer over owned sessions):

- It keys off run state, not events — so re-running a tick after a crash re-attempts an undelivered activation and never double-applies a transition (the transition already happened; delivery is a separate idempotent step). For a PERSISTENT role the activation is complete once the Enter keystroke is emitted (phase `done`). For a FRESH role there is a further DURABLE step: emitting Enter advances the phase to `rebind-pending`, NOT `done`, because the sid rebind (section C) still has to land. The record durably keeps the rebind keys — the pre-`/clear` transcript-dir listing snapshot and the frozen rendered-prompt prefix — until it does, mirroring the TUI keeping `last_delivery` until correlation succeeds (`app.rs:3880`, `:7400`). Only after discovery rebinds `current_session_id` and patches the history entry's `session_id` does the phase become `done`. The baseline (0 for fresh) guards against the gate re-firing, and the gate stays inert (`SkipReason::NoTranscriptId`) throughout `rebind-pending`.
- It ports `submit_prompt`'s body/Enter separation, the PTY-quiet gate, and engine-specific Enter encoding into the daemon. The daemon owns the PTY and the `PtyByteFanout`, so it can observe the output stream to detect quiet windows and track bracketed-paste / kitty keyboard mode the same way the TUI drainer does (resolves open question 2: the daemon maintains the terminal-mode state by observing its own PTY, rather than depending on a TUI). This is the largest single piece of new daemon code.

Rendering moves to finalization (see section A): the poller stops pre-rendering and instead records the raw prompt/source on `pending_activation`, and the drainer renders at finalization from the PRE-reset, pre-append snapshot (before `/clear`, matching the TUI). What moves is both the *rendering* (to the drainer, from that snapshot) and the *delivery* of the prompt.

### B1. Resolver + history-count parity for the shipped `feedback.toml`

The daemon resolver (`DaemonWorkflowResolver`, `poller.rs:1052`) must reach parity with the TUI resolver (`WorkflowResolver`, `controller.rs:260`) for every template variable `feedback.toml` actually uses, or the manager role renders empty sections and makes bad decisions. Two concrete gaps today:

- `{{ rejected_findings }}` (`feedback.toml:22`): the `RoleResolver::rejected_findings` trait method has a default impl that returns empty (`template.rs:77`); the TUI overrides it to return `run.rejected_findings` (`controller.rs:380`), but `DaemonWorkflowResolver` does NOT override it — so on the daemon path `{{ rejected_findings }}` renders empty. The daemon resolver must override it from `self.run.rejected_findings`.
- `{{ roles.<role>.this_turn }}` (`feedback.toml:47`, `:50`, `:66`, `:69`): the TUI's `this_turn` slices messages relative to the activation's `text_messages_at_start` (`controller.rs:312`), but the daemon history append currently passes `text_messages_at_start = 0` (`controller.rs:1647`, `app.rs:4900`), so the slice would be wrong. The daemon must compute and persist `text_messages_at_start` at finalization — using `list_messages(…, Assistant).len()` (the text-bearing count), NOT `count_messages` (the turn count, which over-counts tool-only / thinking-only entries and would mis-slice `this_turn`) — and the daemon resolver must implement the `this_turn` slicing against it, matching the TUI.

The single-source contract is enforced by the existing cross-crate parity test (`daemon_and_tui_resolvers_produce_identical_output`); extend it to cover `this_turn` and `rejected_findings` against a fixture run + `feedback.toml`.

### B2. Daemon-side workflow definition loading

The poller skips with `SkipReason::NoWorkflowDefinition` when `state.workflow_definitions` lacks the run's workflow (`poller.rs:468`). Today that map is daemon in-memory state populated ONLY by the TUI's `workflow.update_definitions` push (`state.rs:406`), and the handler REPLACES it wholesale — `state.workflow_definitions.clear()` then re-insert (`methods.rs:2417`). So a daemon started or restarted with no TUI has it empty (driver can't fire — contradicts the headless goal), AND a TUI reconnect would clobber any daemon-loaded set with the TUI's local one. Fix with a TWO-LAYER model: a base layer loaded from the daemon's own `workflows_dir` (configured in `daemon.toml`, deployed at `/opt/cm-daemon/workflows/`) at startup and re-read on change, plus an override layer fed by the TUI push. Definition lookup checks override then base. Change `workflow.update_definitions` to replace only the OVERRIDE layer (its `clear()`+re-insert stays within that layer), so a TUI reconnect can never clear the base — locally-edited TOMLs still override, but the headless base survives with no TUI in the loop.

### C. Fresh-context respawn moves into the daemon

Port `reset_fresh_session` into the daemon as the step-1 primitive of the finalization in section A: when the pending activation's target role is `Context::Fresh`, the drainer first queues `/clear` (gated on PTY-quiet) or kills + respawns via the daemon's own PTY lifecycle, refreshes the transcript baseline, resets the role `MessageBaseline` to zero, and clears `current_session_id`. The manifest entry (sidebar slot) survives because the session uid is unchanged for `/clear`, or re-registered under the same role binding for a full respawn — same observable behavior as today.

IMPORTANT — daemon-side sid discovery is a NEW component, and it runs AFTER delivery, not before. After `/clear`, Claude rotates its transcript file; the new sid must be rebound to `current_session_id`. Today that rebind is done ONLY by the TUI's content correlator (`resolve_pending_deliveries`, `tui/src/app.rs:7358`/`:7371`): it matches the new `history.jsonl` entry's content prefix against the delivered prompt via the TUI-only `last_delivery` field — i.e. it inherently runs POST-delivery (there is no new content to correlate, and often no new file yet, until the activation prompt has been delivered and the role's first turn lands). A directory-listing diff keyed off the pre-`/clear` snapshot is the other viable mechanism, and it too only resolves once `/clear` has rotated and the new turn appears — also post-delivery. So finalization MUST NOT block on the rebind before delivering. This is safe because a fresh role's post-`/clear` baseline is just 0 (the new transcript is empty), and a fresh role's activation prompt does not read its own new transcript — so the daemon delivers with `session_id` pending and `assistant_count_at_start = text_messages_at_start = 0`, then discovery (content-prefix correlation, mirroring the TUI, or the listing diff) rebinds `current_session_id` and patches the entry's `session_id` afterward. The poller keeps the role's idle gate inert while `current_session_id` is unbound (`SkipReason::NoTranscriptId`), so it never counts against the stale pre-`/clear` transcript and never fires until the new sid is bound and the role completes a turn. Durable across restart: the `rebind-pending` phase persists the rebind keys on `pending_activation` — the pre-`/clear` transcript-dir listing snapshot AND the frozen rendered-prompt prefix — so a daemon that restarts AFTER Enter is emitted but BEFORE the rebind lands resumes discovery from the record (the prefix/snapshot are not lost) and reaches `rebound`/`done`. Discovery is idempotent on that resume (it re-finds the same new file / matching entry). The `/clear` path is preferred over kill+respawn because it keeps `daemon_session_uid` stable and avoids an ownership-gate (`daemon_owns_run`) flicker mid-reset.

### D. Daemon `start_workflow` + a daemon-side command/env builder (resolves reviewer Medium #4)

Add a daemon `start_workflow` RPC that: validates the TOML (already pushed via `workflow.update_definitions`), builds each participant's engine-specific argv/env/cwd with a daemon-side command builder (ported/recreated from the TUI's launcher, since `start_session` itself stays argv-agnostic), spawns participants via its own PTY lifecycle, writes the initial state.json, sets the worker's initial pending activation (delivered via B), and lets the poller drive from there. `mcp_server` re-routes `start_workflow` to the daemon socket; the TUI's `A-f` calls the same RPC.

### E. TUI becomes an observer

The TUI already tails `events.subscribe` and reloads state.json (`tui/src/workflow_watch.rs`). Once A-D land, delete the TUI-tail residual (`deliver_dynamic_activation_prompt`, `reset_fresh_session`, the deferred history append) and the now-always-true `daemon_session_uid` skip gate; keep observer rendering (`app.rs` sidebar grouping + history view). A run progresses with or without the TUI attached.

### Alternatives considered

| Alternative | Why rejected |
|---|---|
| Deliver the activation synchronously inside `workflow_transition` | Delivery must wait for PTY-quiet and schedule a deferred Enter; doing it synchronously under the state flock would block the handler on terminal timing and lose crash-restart idempotency. A durable pending-activation consumed by a drainer matches the existing async PendingWrite model. |
| Have the daemon re-drain events.jsonl to apply transitions | The transition is already applied under flock before the event is written (`methods.rs:3478`); re-applying from the event would double-close / double-increment. Events stay notify-only. |
| Build a new daemon engine/driver module | A daemon `WorkflowPoller` + `DaemonWorkflowResolver` + transcript introspection already exist; a parallel engine would diverge from the shipped gate logic. We extend the poller. |
| Keep delivery in a headless TUI on cm-manager | A second always-on process duplicating PTY ownership; contradicts the TUI->daemon relocation and the daemon already owns the PTYs. |
| Switch reviewer to claude-code to dodge Codex auth | Diverges cm-manager from the local `feedback.toml`; user chose to provision Codex headless auth and keep one definition. |

## Risks and open questions

- Terminal-mode reproduction (the real failure mode the reviewer flagged): the daemon delivery drainer must reproduce bracketed-paste framing and the live-kitty-keyboard Enter encoding that the TUI drainer derives at fire time. Mitigation: the daemon observes its owned PTY's output stream to track the mode (it already fans those bytes out), and Phase 1 validates mode tracking against a recorded byte stream; Phase 3's acceptance is a behavioral delivery test (the target agent actually advances a turn), not a static byte assertion.
- Delivery idempotency across crash/restart: a pending activation half-delivered (body typed, Enter not yet sent) — or, for a fresh role, Enter emitted but the sid not yet rebound — when the daemon restarts. Mitigation: persist the finalization phase (queued / rendered / reset-done / body-sent / rebind-pending / done) AND the full trigger/history metadata AND the fresh-rebind keys (pre-`/clear` listing snapshot + frozen rendered-prompt prefix) on the record, so the drainer resumes at the right step — including resuming sid discovery from `rebind-pending` — without re-reading events; assert both resume cases in Phase 3 tests via the new mid-finalization seam (the existing pre-apply seams + EISDIR trick don't reach this point).
- Two-driver window during migration: until Phase 4, both TUI and daemon could act. Mitigation: every new daemon delivery path is gated on `daemon_owns_run` (already true for daemon-spawned sessions, which the TUI already skips). No flag day.
- History-append parity: the daemon-computed `assistant_count_at_start` must equal the TUI's `compute_role_assistant_count` to keep the on_idle gate from firing on a stale pre-prompt turn. Mitigation: reuse `transcript::count_messages`, compute the count AFTER the fresh reset, and pin with a parity test (Phase 3).
- Resolver / template-variable parity: the daemon resolver must expand every variable the shipped `feedback.toml` uses identically to the TUI, or the manager role gets empty `{{ rejected_findings }}` / `{{ this_turn }}` sections and decides wrong. Two known gaps: `rejected_findings` (daemon uses the empty default impl) and `this_turn` (needs a persisted `text_messages_at_start`, currently 0). Mitigation: override `rejected_findings`, compute/persist `text_messages_at_start`, and extend the cross-crate `daemon_and_tui_resolvers_produce_identical_output` parity test to cover both against `feedback.toml` (Phase 3). Open question: audit any OTHER workflow TOMLs for variables the daemon resolver doesn't yet implement before declaring parity.
- Workflow-definition availability without a TUI: `state.workflow_definitions` is TUI-pushed in-memory state and the push handler REPLACES it wholesale (`methods.rs:2417`), so a daemon with no TUI (cold start or restart) can't drive any run (`NoWorkflowDefinition`), and a TUI reconnect would clobber any daemon-loaded set. Mitigation: two layers — a base loaded from `workflows_dir` and a TUI-fed override — with `workflow.update_definitions` changed to replace only the override (Phase 4). Phase 3's restart test keeps the TUI attached; the no-TUI restart claim lives in Phase 4 where the layering lands.
- Codex headless auth: unverified that `~/.codex/auth.json` alone suffices for non-interactive Codex on the VM. Open question — validate in Phase 5 before declaring acceptance; claude-code reviewer variant is the documented fallback only if Codex headless proves infeasible.
- `cm-tui` is undeployed on cm-manager (gap found 2026-06-05). Open question: build on the VM vs cross-compile locally — resolve in Phase 5.

## Implementation plan

### Phase 1: Daemon PTY-quiet detector + keyboard-mode tracker [feedback]

- **Goal:** The daemon can tell, for a session it owns, when the PTY is quiet and what the current bracketed-paste / kitty keyboard mode is — the inputs delivery needs.
- **Scope:** A consumer over the existing `PtyByteFanout` that maintains per-session quiet timing and terminal-mode state, mirroring the TUI drainer logic in `tui/src/app.rs:6180`/`13710` and `tui/src/agent/mod.rs`.
- **Out of scope for this phase:** Actually sending prompts (Phase 3), respawn (Phase 2).
- **Acceptance criteria:**
  - Replaying a recorded PTY byte stream (mode-set/reset sequences + output bursts) through the daemon tracker yields the same quiet-window and keyboard-mode decisions the TUI drainer computes for the same bytes (parity test with committed fixture).
  - `cargo build --workspace` green; tests pass.
- **Dependencies:** none

### Phase 2: Daemon fresh-context respawn primitive [feedback]

## Testing strategy

- Unit/parity (daemon): PTY-quiet + keyboard-mode tracker parity against a committed recorded byte stream (Phase 1); history-append parity — `assistant_count_at_start` vs `transcript::count_messages` (turn count) and `text_messages_at_start` vs `transcript::list_messages(…, Assistant).len()` (text count, NOT the turn count) — plus `TriggerKind` tagging and the extended `daemon_and_tui_resolvers_produce_identical_output` covering `this_turn` + `rejected_findings` against `feedback.toml` (Phase 3).
- Integration (daemon): fresh-respawn session-id swap + baseline reset + sidebar-slot preservation, exercised directly (Phase 2); headless finalization+delivery — owned worker idle -> poller fire -> fresh reviewer reset, history appended with correct baselines (0 for the fresh reviewer, stable count for a persistent role), raw MCP prompt rendered pre-reset/pre-append (and empty-prompt→template fallback), prompt submitted with the TUI process killed, plus crash-resume-exactly-once (including the Enter-emitted-rebind-pending case) and Codex kitty-Enter (Phase 3); daemon loads definitions from `workflows_dir` and a full run reaches `Done` with NO TUI ever attached, plus a no-TUI daemon restart mid-run that resumes (Phase 4).
- Manual / e2e: the cm-manager acceptance run (Phase 5) — launch, quit local TUI, verify completion over SSH, reattach, verify history. PTY timing and respawn behavior are validated manually here in addition to the daemon integration tests.

## Rollout / migration

Phases 1-3 extend the daemon behind the existing `daemon_owns_run` gate, which the TUI already declines to drive — so during migration the daemon only completes hand-offs the TUI already skips; no flag day, no double-drive, and the single-mutation invariant (transition applied once, under flock, before the event) is preserved throughout. Phase 4 flips launch ownership to the daemon and removes the TUI residual in one coherent change. Phase 5 is deploy + secret provisioning on cm-manager only; state.json / events.jsonl formats are unchanged (the pending-activation record is additive with serde defaults).

# Codex continuation recovery

CM automatically tries native `/fork` when an interactive Codex session stops with `previous_response_not_found` (“Previous response was not found; retry without previous_response_id”). This creates a fresh Codex thread in the same pane, retaining the conversation and the CM session UID, task, workspace, chat identity and board ownership. It does not create another CM worker. `A-R` resumes the existing thread and may encounter the same stale provider anchor again.

The daemon owns recovery, so it works without a connected viewer and two viewers cannot trigger duplicate attempts. The current relay reports the precise error cause. Already-running older relays may expose only `other` or `serverOverloaded`; CM accepts those only when the current rendered terminal shows the exact missing-response error immediately before the Codex composer. Ordinary overload, rate-limit, usage-limit and unrelated errors do not trigger recovery.

Recovery requires a failed foreground turn, a complete empty background-job inventory, no scheduled jobs, and an empty recognized Codex composer. New input, an unsent draft, a changed screen/turn, a handoff or rotation, a shell, a workflow participant or a continuous-task session prevents automatic command delivery. CM never clears a draft or repeats Enter to force recovery.

Keyboard encoding comes from the session's retained keyboard state, which survives replay-buffer eviction and brain restarts. If that state is unavailable, recovery requires keyboard-mode evidence in the current replay; otherwise it is skipped without typing.

CM persists an attempt before sending `/fork`. Duplicate reports, reconnects and daemon restarts cannot repeat that attempt. A changed transcript binding with matching native fork ancestry confirms the fork; once the new thread is idle, CM queues one native recovery notification asking the agent to reconcile its retained context, board, inbox and any in-flight work before continuing. It does not replay the failed user prompt or claim that prior side effects failed. Only a subsequently completed engine turn rearms automatic recovery, so repeated failures cannot form a fork loop.

The daemon journal records the attempt and verified fork. Its durable receipt is beside `daemon-sessions.json`, named `daemon-codex-recovery-<session-uid>.json`, with the source/target transcript and phase. `submitted` means command bytes were sent, not that a new thread was confirmed. `write_failed_or_uncertain` and `cancelled_input_or_state_changed` require manual attention unless a matching fork is subsequently observed; the original error remains visible. Native `/fork` remains available manually if automatic recovery is skipped or uncertain. Do not delete receipts to force an automatic retry without first reconciling the current pane and transcript.

This is a scoped workaround for a lost provider continuation. It does not repair the provider/proxy's stale-anchor behavior. Deployment needs the updated daemon on the session's owning host; no viewer update or agent restart is required for the exact older-relay screen fallback. New or restarted Codex launchers also gain structured error classification.
